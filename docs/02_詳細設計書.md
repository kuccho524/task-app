# 詳細設計書

## 1. システム構成
本アプリケーションはNext.js App Routerを利用したWebアプリケーションである。
画面表示はServer Componentsを中心に構成し、フォーム操作はClient ComponentsからServer Actionsを呼び出して実行する。

認証はSupabase Authを利用する。
Supabase Auth上のユーザーIDを`public.users.user_id`として保持し、アプリケーション内の作成者・担当者判定に利用する。

DBアクセスはPrisma Client経由でSupabase PostgreSQLに接続する。
Project、Task、User、Priority、Status、CommentのデータモデルをPrisma schemaで管理する。

構成概要:

```text
Browser
  -> Next.js App Router
  -> Server Components / Client Components
  -> Server Actions
  -> Prisma Client
  -> Supabase PostgreSQL

Browser
  -> Supabase Auth
  -> Supabase Auth Session Cookie
```

## 4. 認証設計
### 4.1 ユーザー登録
ユーザー登録画面で入力されたユーザー名、メールアドレス、パスワードをServer Actionに送信する。
`signUp` Actionで入力チェックを行い、Supabase Authの`signUp`を実行する。

ユーザー名はSupabase Authのuser metadataに`user_name`として渡す。
アプリケーション用ユーザー情報は`public.users`で管理し、DB側の連携処理により作成される前提とする。

登録成功後は`/login`へ遷移する。

### 4.2 ログイン
ログイン画面で入力されたメールアドレス、パスワードをServer Actionに送信する。
`login` ActionでSupabase Authの`signInWithPassword`を実行する。

ログイン成功後は`/projects`へ遷移する。
ログイン失敗時は画面上にエラーメッセージを表示する。

### 4.3 ログアウト
ナビゲーションのログアウトボタンから`logout` Actionを呼び出す。
Supabase Authの`signOut`を実行し、`/login`へ遷移する。

### 4.4 認証必須画面
`/projects`配下および`/tasks`配下のlayoutで`requireAppUser`を呼び出し、アプリ用ユーザー情報の存在を確認する。
存在しない場合はエラーとする。

`/`ではSupabase Authの認証状態を確認し、未ログインの場合は`/login`、ログイン済みの場合は`/projects`へ遷移する。

## 5. 共通ライブラリ設計
### 5.1 `lib/supabase/server.ts`
Server Components / Server Actionsから利用するSupabaseクライアントを生成する。
`next/headers`の`cookies()`を利用し、Supabase AuthのセッションCookieを扱う。

### 5.2 `lib/supabase/client.ts`
Client Componentsから利用するSupabaseブラウザクライアントを生成する。

### 5.3 `lib/auth.ts`
| 関数名 | 内容 |
|---|---|
| `requireUser` | Supabase Authのログインユーザーを取得し、未ログインなら`/login`へ遷移する |
| `requireAppUser` | Supabase Authユーザーに対応する`public.users`レコードを取得する |

### 5.4 `lib/prisma.ts`
Prisma Clientを生成する。
開発環境では`globalThis`にPrisma Clientを保持し、Hot Reload時の多重生成を抑制する。

### 5.5 `lib/progress.ts`
Taskの完了状態をもとに、総数、完了数、未完了数、進捗率を計算する。

### 5.6 `lib/permission.ts`
作成者とログインユーザーの一致判定、およびProject削除可否判定を行う。

### 5.7 `lib/dateFormat.ts`
日付および日時を`ja-JP`形式で表示する。

### 5.8 `lib/validation.ts`
開始日と期限日の前後関係を検証する。

## 6. Server Actions設計
Server Actionsは外部から直接POSTされる可能性があるため、必要なAction内で認証・認可を確認する。

### 6.1 `authActions.ts`
| 関数名 | 内容 | 成功時遷移 |
|---|---|---|
| `signUp` | ユーザー名、メールアドレス、パスワードでSupabase Authに登録する | `/login` |
| `login` | メールアドレス、パスワードでログインする | `/projects` |
| `logout` | ログアウトする | `/login` |

### 6.2 `projectActions.ts`
| 関数名 | 内容 | 主な認可 |
|---|---|---|
| `createProject` | Projectを作成する | ログイン済みユーザー |
| `updateProject` | Projectを更新する | 作成者のみ |
| `deleteProject` | Projectを削除する | 作成者のみ、関連Taskなし |

Project作成時、`assignee_id`と`created_by`にはログイン中のアプリユーザーIDを設定する。
ステータスが完了扱いの場合、`completed_at`に現在日時を設定する。
未完了扱いの場合、`completed_at`は`null`とする。

### 6.3 `taskActions.ts`
| 関数名 | 内容 | 主な認可 |
|---|---|---|
| `createTask` | Taskを作成する | ログイン済みユーザー |
| `updateTask` | Taskを更新する | 作成者のみ |
| `deleteTask` | Taskを削除する | 作成者のみ |

Task作成時、`assignee_id`と`created_by`にはログイン中のアプリユーザーIDを設定する。
Project詳細画面からTask作成画面に遷移した場合は、`redirectTo`をhidden inputとして保持し、作成後にProject詳細画面へ戻る。

### 6.4 `commentActions.ts`
現時点では未実装。
CommentモデルはDB schema上に存在するが、コメント投稿・表示の画面およびActionは実装していない。

## 9. 検索・絞り込み設計
検索・絞り込み条件はURLクエリパラメータで保持する。
Server Componentの`searchParams`を参照し、Prismaの`where`条件に変換する。

### Project一覧
| クエリ | 内容 |
|---|---|
| `keyword` | Project名・説明の部分一致検索 |
| `statusId` | Statusによる絞り込み |
| `priorityId` | Priorityによる絞り込み |
| `assigneeId` | 担当者による絞り込み |

### Task一覧
| クエリ | 内容 |
|---|---|
| `keyword` | Task名・説明の部分一致検索 |
| `projectId` | Projectによる絞り込み |
| `statusId` | Statusによる絞り込み |
| `priorityId` | Priorityによる絞り込み |
| `assigneeId` | 担当者による絞り込み |

## 10. 完了状態・進捗計算設計
完了判定はStatus名ではなく、`statuses.is_completed`で行う。
ProjectまたはTaskのステータスが完了扱いの場合、`completed_at`に現在日時を設定する。
完了扱いでない場合は`completed_at`を`null`にする。

Project進捗率は以下で計算する。

```text
進捗率 = 完了Task数 / 関連Task総数 * 100
```

関連Taskが0件の場合、進捗率は0%とする。
